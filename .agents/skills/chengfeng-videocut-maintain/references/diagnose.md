# 排查模式

目标是定位故障层，不把一切称为“没安装”。先读[公共接入](shared/plugin-access.md)，涉及工程时读[CLI 合同](shared/runtime-cli.md)。按实际问题取证，不每次强制跑全部检查。

## 最少取证

取得真实命令、报错、OS/架构、安装来源/通道和启动器位置；展示时脱敏路径、项目名与凭据。从安装记录或用户入口开始，不扫描端口、搜密钥或启动第二服务。

1. 核对 Skill 文件与宿主加载、同名提供者；文件可读不证明 Runtime 已装。
2. 以参数数组运行已确认启动器的 `--help`、`workbench commands --json`，必要时 `doctor --json`；不直接启动服务。
3. 有用户指定或已确认安装记录中的显式 endpoint 才 connect，核对产品、版本、PID/build 和需要的 API；不换到另一个能连的项目。
4. 项目问题以服务器 projectId 读取 workflow/具体资源及 revision；异步卡住用原 jobId/operationId 查，不重新提交。
5. 预览问题比较保存结果与页面项目/版本、资源请求和可见状态。刷新前保留未保存编辑；不删层、改源或清空整个缓存掩盖问题。

## 常见分界

| 证据 | 判断与下一步 |
|---|---|
| Windows PATH 无 Bun/FFmpeg，但受管路径可运行 | 不算缺依赖，继续查真正报错 |
| npm.ps1 被执行策略阻止 | 仅当前渠道确需 npm 时，用已有 npm.cmd/npx.cmd 的受支持调用方式；不降低系统策略 |
| EPERM/EACCES、旧 cli.js 不可读 | 权限、占用或防护均可能；不单凭错误确定原因，不删除受管根、不关闭安全软件 |
| --help 正常，workbench 命令不存在 | Runtime 缺实现；更新 Skill 文字无效 |
| connect 超时或拒绝 | 检查显式地址与服务归属，不杀未知 PID 或另起实例冒充恢复 |
| job 运行但进度不变 | 记录同 job 的时间、阶段及只读日志；unknown 不等于未提交，不换 ID 重跑 |
| JSON 新 revision、页面旧画面 | 区分保存、通知、资源和播放器刷新；回读不等于像素通过 |

## 修复与回读

只问原因时交付现象、直接证据、原因判断与建议。要求修复时优先可回退的最小操作；停服务、迁移安装、下载、付费云任务或覆盖配置须在已授权范围内且目标准确，超出范围先确认。

只有用户要求更新、或已批准诊断提出的更新方案时才读[更新模式](updates.md)，不要求另装检查更新 Skill。业务判断交回对应 Skill；修运行条件不应改项目。没有已验证修复路径就报告，不自制旁路写入器。

修后重跑原失败检查，回读同一项目/任务；涉及预览时检查真实画面。分开报告文件、CLI、服务、业务与画面结果；重复失败保留证据并重新定位，不循环重装。要求公开反馈才读[Bug 反馈](report-bug.md)，先脱敏并确认。
